# 3. 色・画像・余白

UIB（2 章）は、色や画像を「番号」で参照しています。番号が指す中身は、同じ `mailres2.dll` の別の種類のリソースにあります。こちらも独自の形式なので、`uxcore.dll` の読み込み処理から形式を読み取りました。仕様の全体は [spec/resources.md](../spec/resources.md)（英語）にあります。

## リソースの種類

| 種類 | 中身 | 読んだ関数 |
|---|---|---|
| 4000 | 画像などの「見た目の値」。PNG、独自の RLE 画像、色、テーマ部品の描画指定など | `FUN_1010abd4` |
| 4002 | 色 | `CRMColorResource::Load`（0x101135df） |
| 4003 | 長方形（設計時の DPI 付き） | `FUN_1011718d` |
| 4006 | PNG の 9 分割の余白とコマ数、または RLE の配色用の対 | `CreateImageValueUsingGDIPlus`（0x1010af88） |
| 4008 | アニメーション（コマの並びと時間） | `CreateAnimationValue`（0x1010a220） |
| 4009 | 文字列の差し替え（別の番号へ飛ぶなど） | `CRMStringResource::Load`（0x1011424d） |
| 4011 | PNG のシート（スプライトの元画像） | `FUN_101302d5` |
| 4012 | スプライト（シートの中の長方形、回転、コマ） | `FUN_1012e88d` |

どのレコードも、先頭の 1 バイトで種類が決まります。`C` はふつうの色、`D` は配色に合わせて変わる色、`S` はシステムの色、`J` は別の番号へ飛ぶ、`N` は無し、といった具合です。[観察]

## 独自の RLE 画像

`mailres2.dll` の画像 1,159 個のうち 514 個は、`RLE` で始まる独自の圧縮形式でした。いちばん手間がかかったのがこの形式です。

- 1 枚の画像は、9 分割の枠（左上・上・右上……）の「部分」に分かれて入っています。どの辺に余白があるかを 4 ビットで表し、その組み合わせで部分の数が決まります。
- 各部分は、行ごとの開始位置の表と、ビット単位の圧縮列です。R・G・B（と透明度）の 3〜4 枚の面が交互に入っていて、「いちばん進んでいない面から次の連続を読む」という規則で並んでいます。
- 連続の種類は 4 つです。同じ値で埋める、値をそのまま並べる、前の値からの差（増える／減る）を並べる。
- 1 色 5 ビットのものと 8 ビットのものがあります。配色に合わせて色を変える画像は、色相の無い「彩度と明るさ」だけを持っています。

Ghidra は一部の関数でループを落としてしまったので、そこは逆アセンブリを直接読みました。デコーダー（`tools/resources/rle.py`）は自分で答え合わせをします。1 行読むごとに、読み終わった位置が次の行の開始位置とぴったり合うことを確かめます。514 個すべてがこの検査を通りました。並べた画像を目で見ても、アイコン、顔文字、枠、窓のボタンが正しく出ていました。

## 9 分割の枠

ボタンや枠の画像は、四隅はそのまま、辺と中央だけを伸ばして使います（9-slice）。PNG の画像では種類 4006 に左・上・右・下の余白が入っています。RLE の画像では、最初の部分の幅と高さ、最後の部分の幅と高さが、そのまま余白になります。[観察: `FUN_100ea3e6`]

作り直したアプリでは、この余白を CSS の `border-image` に当てはめました。

## 配色（カラー）

Windows Live メールには、ウィンドウの色を 12 色から選ぶ機能がありました。

- 色が変わる部分は、`D` の色と、彩度・明るさだけの RLE 画像で描かれます。
- 選んだ色の**色相**だけを取り出し、保存されている彩度・明るさと組み合わせて、HSL から RGB に戻します。`tools/resources/colorize.py` は、この計算を `uxcore.dll` と同じ手順（`FUN_1011365f`、`FUN_101133cb`）で再現したものです。
- 12 色の候補は `uxcore.dll` の 0x10249fb8 の表にあり、色の番号 20480〜20491 を指しています。[観察]
- 既定の配色が何色かは、たどりきれていません。保存されている色がすでに「Live の青」（色相およそ 213°）なので、配色なしのまま使うのが既定に近いと推定しています。[推定]

## テーマの上書き

`vista.thm` や `mailhc.thm`（ハイコントラスト用）は、同じ種類の番号を持つリソースだけの DLL です。先に登録された方が優先されるので、テーマを重ねると一部の色や画像だけが差し替わります。ハイコントラスト用のものは、ほとんどがシステムの色（`S`）でした。[観察]

## デコーダー

```bash
python3 -I tools/resources/decode_resources.py out/
```

`targets/Windows Live/` に置いたインストール済みのファイル（`mailres2.dll` と `.thm` 5 個）を読みます。結果は `out/` に書き出します。

- 色の表（`colors.json`）。飛び先を解決済みで、配色 12 色それぞれの値も付けます。
- 画像（PNG）と、その余白・コマの情報。
- スプライト（回転を戻したもの）。

全モジュールのすべての項目を、エラー 0 で読めることを確かめました（件数は spec/resources.md の表）。書き出した画像は Microsoft の著作物なので、このリポジトリには入れていません。
