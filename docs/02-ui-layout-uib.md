# 2. 画面の設計図（UIB）

Windows Live メール 2012 のメイン画面は、ふつうの Windows のコントロールではなく、**DirectUI** という Microsoft 社内の画面部品で描かれています。メッセージ一覧の行の高さ、フォルダー ウィンドウの余白、選択したときの色などは、プログラムに直接書かれていません。`mailres2.dll` の中の、**種類 4010 のリソース**に入っています。

このリソースを開くと、先頭が `UIB\0` で始まる、見たことのない形式でした。公開された資料は見つからなかったので、読み込む側のコードから形式を逆算しました。仕様の全体は [spec/uib-format.md](../spec/uib-format.md)（英語）にあります。

## 入口を見つける

1. `rea inspect-pe-resources` で `mailres2.dll` のリソースを一覧にすると、種類 4010 が 29 個ありました。どれも先頭は `UIB\0`、続く 2 バイトは `1` です。
2. `uxcore.dll` を逆コンパイルし、`"UIB"` の 4 バイトを `memcmp` で比べている関数を探しました。`FUN_100c074a` が見つかりました。違えばエラー `0x80004005` を返し、版が 1 でなければ `0x8000FFFF` を返します。[観察]
3. この関数を呼んでいる側をたどると、`CRMDUIParser` というクラスに行き着きました。名前の付いた画面の部品（テンプレート）を作るための、読み込みと実行の役です。

## わかった形

UIB は「画面の木を組み立てるための、小さなプログラム」でした。

- **ヘッダー**（0x28 バイト）に、7 つの区画の開始位置が並んでいます。
  - 文字列プール
  - クラス名の表
  - プロパティ名の表
  - 入口（テンプレート名 → コードの位置）
  - 共有の断片
  - リソースの参照
  - コード本体
- **コード**は、値をスタックに積んで処理する、命令 1 バイトの仮想機械です。
  - 「要素を作る」「値を作る」「プロパティに入れる」「子として足す」などの命令が、合わせて 40 個ほどあります。
  - 命令の実行は `FUN_100c1c0c` が 1 命令ずつ分岐して行います。各命令の処理関数を 1 つずつ読んで、何を取り出して何を積むかを表にしました。[観察]
- **落とし穴**: ヘッダーや表の数は**リトル エンディアン**なのに、命令の直後に埋め込まれた数だけは**ビッグ エンディアン**です。逆コンパイル結果の `CONCAT11(ip[1], ip[2])` という書き方でわかりました。[観察]
- **色**は `0xAABBGGRR` です。Windows の COLORREF の上の 1 バイトに透明度を入れた形です。[観察]
- **大きさ**には、画面の拡大率（DPI）に合わせる命令が使われています。`dpi(x)` は `MulDiv(x, dpi, 96)`、フォントのポイントは `-MulDiv(pt, dpi, 72)` です。設計図に入っているのは 96 DPI（拡大率 100%）のときの値です。[観察]

## 状態ごとの見た目（シート）

行を選んだとき、マウスを乗せたとき、窓が非アクティブのときの見た目は、**シート**という規則の集まりに入っています。CSS に似ています。

- 規則は「どのクラスに」「どんな条件のとき」「どのプロパティを何にするか」の 3 つの組です。
- 条件の比べ方は 3 種類です。等しい（0）、等しくない（1）、ビットが立っている（2）。行の状態（選択中、未読など）はビットの組み合わせで表され、`Tag&65536` のような条件で調べます。[観察: `FUN_100b4fdb`]
- 当てはまる規則のうち、最初の 1 つが使われます。並び順は、条件の細かさの順だと推定しています。[推定]

`tools/rules.py` は、変換した XML からクラス名とプロパティで規則を絞り込んで一覧にします。たとえばメッセージ一覧の行で「選択中かつ非アクティブ」のときの背景色を調べる、といった使い方をしました。

## デコーダー

`tools/uib/uib2xml.py` は UIB を読みやすい XML に変換します。

```bash
python3 -I tools/uib/uib2xml.py --check 7001_1033.bin      # 全バイトを読めたか確かめる
python3 -I tools/uib/uib2xml.py 7001_1033.bin -o 7001.xml  # XML にする
```

- 29 個すべてで、**すべてのバイトを読み、未知の命令が 1 つも無い**ことを `--check` で確かめました。
- リソースを参照している値には、インストール済みの DLL から読んだ実際の値（色、文字列、数）を `{=…}` の形で添えます。
- 8 個のファイルでは `UXEditMenu` という入口が壊れていて、実行すると必ず失敗します（値を積まずにプロパティを入れている）。デコーダーはこれを `_error` として残し、先へ進みます。[観察]
- どこからも呼ばれないコードの塊が残っているファイルもあります。同じテンプレートの重複定義を、コンパイラーが捨てずに残したものと推定しています。[推定]

## 作り直しに使った値

この設計図から、たとえば次のような値を取り出して、作り直したアプリの CSS に入れました。

- メッセージ一覧の行の高さと余白、1 行表示と 2 行表示の切り替え
- 未読の行の太字、選択中の行の色（アクティブと非アクティブ）
- フォルダー ウィンドウの字下げと件数の表示
- 閲覧ウィンドウの見出しの配置
- 状態バーの区切り

行の高さのように、数を文字列リソース（例: `"45"`）に入れておき、`resint` 命令で数に変えて使っているものもあります。設計図だけでは値がわからず、文字列表とつなげて初めてわかります。
